# 05 — 理解度確認と演習

## 問題

1. `user`と`signature`の役割の違いは何か。メールアドレスの単純なSHA-256ダイジェストだけでは、なぜ改竄を防げないのか。
2. `expiration = now + 1800`とする理由を述べよ。発行からちょうど1800秒後は有効か。
3. `GET /verify/email`の検証順序（署名→期限→現在のメール）を説明せよ。
4. 利用者がアカウント登録後にメールアドレスを変更した。元の宛先へ送ったURLは、期限内でも認証できるか。
5. `Mailer`インターフェースを使う理由は何か。`LogMailer`成功とSMTPメール受信成功は同義か。
6. `RequireVerified`の戻り値を説明せよ。未ログイン、未認証、認証済みの3ケース。
7. `hash_equals()`が使われる箇所を探し、普通の文字列比較との関係を述べよ。
8. `App::register()`で`password_hash()`を使う理由と`password_verify()`の用途を説明せよ。
9. `SqliteUserRepository::claimSendSlot()`に条件付きUPDATEを採用した理由を説明せよ。
10. Web画面で再送ボタンを押してもメールログが増えない。最初に確認する要素を3つ挙げよ。

## 改修課題

**A**（小規模）：現在の60秒の再送制限を90秒に変更する。変更前後に確認すべきテストは何か。`VerificationService::sendVerificationEmail`の第3引数を変更し、テスト時刻も変更する。

**B**（小規模）：ログイン後、認証済みであればダッシュボードに遷移する処理は`App.php`のどこか調べ、その条件判定を説明する。

**C**（デバッグ）：次のように改変した場合、どのような問題が起きるか。

```php
return hash_hmac('sha256', $message, 'hard-coded-secret');
```

**D**（デバッグ）：`ValidateExpiration`の`>`を`>=`へ変えたら、期限のちょうど境界でどう動くか。

**E**（発展）：SQLトランザクションを取り除き、「ユーザーを検索→別リクエストでメール変更→旧メールのURLで認証完了」という並行実行を考える。何が不正なのか。

## 模範解答・解説

1. `user`は入力メールのダイジェスト。`signature`は秘密鍵で計算されるHMAC。SHA-256は誰でも計算できるため、秘密鍵なしでは正しいメッセージの証明にならない。
2. 30分は`30×60=1800`秒。条件は`expiration > now`なので、ちょうど1800秒後は期限切れ。
3. 最初に署名で`id/user/expiration`の真正性を確認し、有効期限を確認し、DBの**現在のメール**と`user`が一致する場合だけ`email_verified`を更新する。
4. できない。DBの現メールのSHA-256と旧URLの`user`が一致しなくなるため。
5. 配信手段を切り替え、SMTPのない状態でも認証ロジックをテストするため。開発ログ記録はSMTP送信・相手の受信成功を意味しない。
6. 未ログインなら`/login`への303レスポンス、未認証なら`/verify/resend`への303レスポンス、認証済みなら`null`を返して画面表示を継続する。
7. `SignedUrl::validSignature`で署名を、`Csrf::valid`でCSRFトークンを、`SqliteUserRepository`でメールのダイジェストを照合している。`hash_equals`は文字列比較のタイミング差から情報が漏れる危険を減らす。
8. 平文パスワードをDBに保存しないため。ログイン時は`password_verify()`で入力したパスワードと保存済みハッシュを照合する。
9. SELECT→別のUPDATEだと同時リクエストが送信間隔の条件を同時に通過する恐れがある。SQLの一回の条件付きUPDATEにより送信枠取得を原子的に判定する。
10. `MAIL_TRANSPORT=log`か、60秒以内か、`email_verified=1`かを確認する。必要ならPHPサーバーログとSMTP設定も確認。

**A**：第3引数を`90`とし、テストの59秒・60秒の境界を89秒・90秒に修正。変更後に`php tests/run.php`を実行。

**B**：`App::login()`の`return (int) $user['email_verified'] === 1 ? ...`。DBの列の値により302ではなく303リダイレクト先を選んでいる。

**C**：秘密鍵がソースから露出し、誰でも正しいURLを作れる。`.env`で256ビット乱数の鍵を管理し、公開リポジトリへ入れてはいけない。

**D**：期限のちょうど境界を有効として扱ってしまい、設定した「発行時刻から1800秒未満」の条件から逸脱する。

**E**：ユーザーを読み取った直後に他リクエストがメールを書き換えると、その後のUPDATEが古いメールに基づいて現在のユーザーを認証済みにできる可能性がある。読取りと更新を同一トランザクションで行う必要がある。
